# Архитектура

## Почему плагины вне процесса

1. **Нет стабильного ABI у Rust.** Гуишка, собранная rustc A, не может
   загрузить `dylib`, собранный rustc B — раскладка типов и vtable
   различаются между версиями компилятора. Каждый плагин пришлось бы
   пересобирать под каждую сборку RESQ-kit. Сетевой протокол такой связки
   не требует.
2. **Изоляция сбоев.** Кривой аналитический проход (экспериментальный
   декомпилятор, паникующий на вырожденном CFG) не должен ронять гуишку.
   Смерть дочернего процесса — сообщение об ошибке, а не потеря сессии.
3. **Свобода языка.** Формат — один JSON-объект на строку. Плагин можно
   написать на Rust, Python, Node — на чём угодно, что умеет читать stdin
   и писать в stdout.
4. **Агенты — полноправные хосты.** Тот же протокол, по которому гуишка
   общалась бы с плагином, уже говорят MCP-клиенты (Claude и др.). Плагин,
   написанный один раз, обслуживает обоих.

## Топология

```text
+--------------------+     newline-delimited JSON-RPC 2.0      +-----------------+
| хост               | <--------------------------------------> | процесс плагина |
| (resq-gui, агент,  |            stdin / stdout                 | (resq-mcp, ...) |
| человек через pipe)|            логи -> stderr                 |                 |
+--------------------+                                           +-----------------+
```

Хост находит плагины, сканируя каталог плагинов на `resq-plugin.toml`
(модуль `manifest`), запускает лежащий рядом исполняемый файл и ведёт
протокол. SDK определяет контракт; встраивание в resq-gui — забота хоста
(в планах).

## Жизненный цикл

1. **spawn** — хост запускает исполняемый файл плагина.
2. **хендшейк** — либо MCP `initialize` (согласование возможностей), либо
   минимальный RESQ `initialize` (эхо версии протокола, модуль
   `handshake`).
3. **сессия** — трафик запросов/ответов; уведомления для односторонних
   событий.
4. **shutdown** — хост закрывает stdin; плагин видит EOF в `serve_stdio`,
   сбрасывает буферы и выходит. Никакого отдельного метода «shutdown» не
   требуется.

## Версионирование

- `resq-plugin-sdk::PROTOCOL_VERSION` (сейчас `1`) покрывает RESQ-соглашения:
  фрейминг, манифест, дисциплину кодов ошибок, форму хендшейка.
- Схемы методов конкретного плагина (например, MCP-инструменты) версионирует
  сам плагин (semver в манифесте + `protocolVersion` MCP для MCP-серверов).
- Аддитивные изменения (новые методы, новые опциональные поля) не поднимают
  `PROTOCOL_VERSION`.

## Что SDK НЕ делает

- Не сканирует каталоги плагинов — хосты делают это через
  `manifest::Manifest::load_dir`.
- Не встраивается в гуишку — см. выше.
- Не хранит состояние — сессии принадлежат процессу плагина; держите
  состояние в памяти или в sidecar-файлах рядом с анализируемыми
  артефактами.
